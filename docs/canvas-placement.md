# キャンバス上の配置ルール

want がキャンバスのどのセルに置かれるかは、デプロイ時にサーバー側のフックが決めます
（`engine/server/handlers_want_hooks.go`）。関係するラベルは4つです。

| ラベル | 意味 |
|---|---|
| `mywant.io/canvas-x` / `-y` | アンカーセルの座標 |
| `mywant.io/canvas-rotation` | 0=右 / 90=下 / 180=左 / 270=上 |
| `mywant.io/canvas-length` | アンカーから先に伸びるセル数（0 = 1マス） |
| `mywant.io/canvas-near` | 「誰の隣に出すか」。座標の代わりに書く |

## 座標が指定されている場合

`canvas-x` / `-y` があれば、まずそのセルを試します。フットプリント（rotation と
length から求まる全セル）が埋まっていれば、チェビシェフ距離のリングを外側へ広げて
一番近い空きセルを探します。

## 座標がない場合

(0,0) から幅10で左→右、上→下に走査して最初の空きセルに置きます。**単に空いている
場所**であって、プレイヤーの近くではありません。デプロイ用の YAML は書かれた時点で
プレイヤーがどこにいるか知りようがないので、これが既定の挙動です。

## `mywant.io/canvas-near`：意図で書く

デプロイファイルが知っているのは座標ではなく「この want は誰のためのものか」だけ
です。両方を知っているのはサーバー（全プレイヤーの現在位置を保持している）なので、
翻訳はサーバー側で行います。

```yaml
metadata:
  labels:
    mywant.io/canvas-near: chr-9eca4b3d   # キャラクターID、または "cursor"
```

`CanvasNearHook` が `CanvasCoordinateHook` の前に走り、次の順で位置を解決して
`canvas-x` / `-y` を書き込みます。新しい情報から順に問い合わせます。

**キャラクターIDを指定した場合:**

1. **ライブカーソル** (`GET /api/v1/cursors` と同じテーブル) — タブを開いている
   本人が「今ここにいる」と報告している位置。TTL 切れは無視されます。
2. **gui_state の `canvas_cursor_{x,y}_<id>`** — 誰もプレイしていないキャラクターが
   最後に置かれた位置。

**`cursor` を指定した場合**（＝「今操作している人の隣」。特定の誰かではない）:

1. **ライブカーソルのうち最後に動いたもの**。ブラウザが位置を publish している人が
   操作している人であり、2人いるなら直前に動いた方がこれをデプロイした人です。
2. **gui_state の無印 `canvas_cursor_{x,y}`**（CursorMan）— ただし
   `cursor_visible` が true のとき **だけ**。これは 0 が初期値の普通の gui_state
   キーなので、CursorMan を一度も出していない盤面では自信満々の (0,0) として
   読めてしまいます。未設定のキーは座標ではありません。

置かれるのは**半径1から**探した空きセルです。本人が立っているセルちょうどに置くと
盤面がプレイヤーを飲み込んだように見えるため、真上ではなく隣に出します。

- `canvas-x` / `-y` を明示していれば、そちらが勝ちます（より具体的な指定なので）。
- 対象が見つからない・一度も位置を持ったことがない場合はエラーにせず、通常の走査に
  委ねます。デプロイを失敗させるほどのことではなく、この機能が無かった頃と同じ場所に
  置かれるだけです。
- 同一バッチ内の他の want も占有セルとして数えるため、3つまとめてデプロイしても
  重なりません。
